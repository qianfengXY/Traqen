# F001 规模试点：逐文件处置事务开销

## 1. 报告人与复现

砚砚 / gpt-6-astra 在实现验收中发现。使用隔离 PostgreSQL 16.15、受控 HTTPS Git 仓库和生成目录，运行：

```sh
node src/cli/source-truth-pilot.js --files-per-source 50000 --postgres-bin <隔离工具链bin> --max-tree-rss-mib 1024 --max-tree-fds 1024
```

预期：在本次已声明的 3600 秒托管时限和资源预算内，验证三个完整版本、仅变化字节上传、来源移走并重启数据库后的历史重放。此时限是本地验收预算，不是产品性能承诺。

实际：`a1292a3` 在首版采集中超时；小文件单次内容写入优化后的 `3552b16eac1d578ca6286fcdba0bc0ade6904a52` 已完成三次冻结，但仍在离线重放阶段达到 3600 秒，没有最终 `PASSED`。不能将已冻结、已传完字节或小规模通过当成完整 100k 验收通过。

第二次超时采样峰值：Node RSS 276512768 字节，进程树 RSS 433586176 字节，进程树 FD 621；采样错误 0。尚不能据此排除未采样的瞬时峰值。原失败记录保留，不提高预算掩盖问题。

## 2. 定位证据

调用链：`SourceCaptureRunner.capture/captureGitFiles → SourceMaterialRepository.dispose → withLease → 当前权限/租约/来源/条目校验 → UPDATE → COMMIT`。

内容已经逐文件校验，但每个 Git 文件及可复用目录文件还独立提交一次处置事务。现有清单枚举已使用有界批量写入，处置没有采用相同的事务粒度。

在同一隔离工具链、Git 100＋目录 100 文件、完整三版本流程上，用 `test/support/source-truth-profile.js 100` 测量（嵌套时间重叠，不可相加）：

| 采集阶段测量 | 修改前 | 批量处置后 |
|---|---:|---:|
| 处置调用 | 310 次单条 | 11 批 |
| 处置调用累计耗时 | 1346 ms | 107 ms |
| SQL BEGIN（含状态迁移） | 315 | 16 |
| SQL SELECT | 1936 | 142 |
| CAS 校验调用 | 501 | 501 |
| 采集总耗时 | 3757 ms | 2203 ms |

单次前后计时受主机负载影响，仅用于定位；事务数下降与校验数不变由回归保护，不向 100k 或部署环境外推速度。其他阶段仍有内容读写、完整清单遍历和准入重验成本。

## 3. 修复内容与安全约束

- 元数据处置最多 500 项/事务；采集使用原有最多 100 项的分页，Git 保留原批次字节上限。
- 每批重新进入原有 `withLease`，校验当前维护权限、任务 generation、租约与恢复状态，并锁定冻结清单中的精确条目。
- 全批先验证，再执行批量 UPDATE。重复路径、缺失条目、内容不符、终态改写或数据库错误都不能留下部分处置。
- 单条上传发布仍走原事务路径；共用同一个处置校验函数。没有新增允许客户端宣称 VERIFIED 的接口。
- 保留 Git 原生对象校验、CAS 全字节校验和取消检查；后续原生帧损坏或取消时，本批不确认任何处置。已写入但未确认的 CAS 不等于已冻结包。
- 不改变 Receipt、Gap、用户确认或 F002 准入契约；不提高超时、并发、内存或 FD 限额。

## 4. 验证

- RED：205 个已存在 CAS 的目录文件在采集阶段发生 206 次租约事务，断言“3 批处置＋1 次迁移”失败。
- GREEN：同一测试变为 4 次事务，仍逐文件校验，全部处置完整且没有自动发布 Bundle。
- 无效批次、重复重试、数据库触发器失败回滚、租户隔离、权限撤销、旧 generation、取消后拒绝写入均通过。
- 真实 PostgreSQL 多连接验证：提交前其他连接看不到批内任何处置；先取得权限栅栏的撤权事务提交后，后到批次被拒绝。
- 定向命令包含 material、capture、postgres、git-batch、upload 五个测试文件：31 项通过、0 跳过；另一次 git-batch 四项通过，包含新增“后续原生帧损坏/取消不提交批次”测试。
- 修改后 Git 100＋目录 100 的三版冻结、增量传输和来源离线重放校准 `PASSED`。语法检查及 `git diff --check` 通过。
