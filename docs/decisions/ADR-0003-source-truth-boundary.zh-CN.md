# ADR-0003：Source Truth 边界与下游准入

> 本轮仅维护中文；[英文旧版](ADR-0003-source-truth-boundary.md)为历史参考。2026-09-06 获得方案确认与“仅更新设计文档”授权，不授权代码或部署。

## 背景

F001 是存量系统分析的证据底座。没有明确来源边界时，一次扫描可能在可移动 branch、实时本地目录或静默不完整的子集上完成；下游事实和语义主张表面可追溯，实际却指向可变或未知输入。

co-creator 已于 2026-08-30 授权 F001 的最终来源模型：固定 Git 版本、上传目录或二者可构成一个版本化来源底座。本 ADR 记录一份来源 Receipt 能被 F002 使用，并经由 F002 provenance 供 F003–F004 使用所需的产品边界。

## 决策

1. 一份 Source Truth 底座是不可变的 Workspace 范围 `SourceBundleSnapshot`，至少包含一个组件：一个已获只读授权的 Git 组件、一个已验证的上传目录组件，或二者同时存在。首期每种组件至多一个。
2. Git 组件必须在采集前由请求的 branch、tag 或 ref 解析到精确的已提交版本。其声明范围默认整个已提交仓库，或一个可选的仓库目录根。
3. 目录组件是由用户选择并传入 Traqen 受控存储的文件夹。只有每个已选文件均被接收且验证后，上传才成功；其内容寻址 manifest 而不是原始本地路径是不可变身份。
4. 组合来源包是带命名空间的并集，而非覆盖。不同组件中同名路径保持不同产物；任何组件都不得被表达为另一类组件的原生身份。
5. 每个已密封版本在逻辑上完整且不可变。后续 Git commit 或目录选择会创建新的组件/来源包/Receipt。未变化的已验证 blob 可在租户/Workspace 策略边界内物理复用；派生的新增/修改/删除 Delta 永不取代完整 manifest 的权威性。
6. 采集只读且安全：不运行仓库提供的代码、hook、构建、依赖安装、不受信任 filter 或上传内容；来源身份、边界、完整性、路径或策略条件不可信时安全关闭。
7. 声明范围内每个已发现条目都有一个明确处置。缺失、排除、脱敏、外部、不可读或失败材料持续可见，并可产生 `CoverageGap`。非阻断 Gap 仅可由负责人、理由和有效期接受；它仍然可见且被继承。身份、初始目录完整性、完整性、路径边界、策略和篡改失败均为阻断。
8. `SourceTruthReceipt` 分别表达组件身份、范围、完整性、覆盖、Gap 接受、版本谱系和一种可消费状态：`READY`、`READY_WITH_ACCEPTED_GAPS` 或 `BLOCKED`。只有 F002 可直接消费合格 Receipt/来源包并继承相关 Gap。F003 和 F004 仅通过 F002 持久化输出获得 F001 provenance。
9. 在大规模下，采集冻结 manifest，经有界资源流式处理，对账 inventory/Gap/总数并原子 seal。草稿或部分材料绝不对 F002 可见。
10. 首期采用单部署节点的专用持久化文件卷保存字节、PostgreSQL 保存 manifest 分片与所有任务/版本/接受/Receipt 记录。不同时支持多个存储后端，不以浏览器或项目 assets 作为存储。内容复用限定在同 Workspace；查询索引和 Delta 可重建，不构成第二套清单权威。
11. 八站顺序固定为：添加来源 → 配置范围 → 自动预检 → 枚举材料 → 冻结清单 → 采集与校验 → 核对清单与有效接受 → 冻结来源包。第 5–6 站只是私有准备结果，整包仅在第 8 站发布。文件先持久化并保护引用，再在数据库事务内发布整包与 Receipt；不假设数据库和文件卷构成同一事务。
12. 一个 Workspace 首期只有一条活动采集。关闭页面不取消任务，未收到的目录字节需客户端重新授权/选择；完整核对原输入后才续传。瞬态失败的新 run 可复用已验证检查点，变动输入不能冒充原输入重试。最终化不可取消；重复发布幂等、响应丢失先查询结果，旧版始终不被新失败改写。
13. 接受由有权限成员操作，记录责任/理由、服务端时间、用户选择的绝对期限，并绑定具体候选/策略/Gap。冻结和每次准入均重验；期限不得平移。冻结内容与当前准入分离，同内容续签仅追加接受和新 Receipt，旧证据不变；损坏、权限和安全阻断不能通过续签接受绕过。
14. 冻结历史、可恢复任务和审计默认 TTL=0。容量不足阻止新写入并给恢复动作，不自动删历史。字节回收须有明确处置授权且无历史、任务或备份引用；物理复用不削弱逻辑完整历史。
15. PostgreSQL 与其引用的 Git/目录内容必须配套备份到独立故障域，并以一致性水位和完整校验闭合。不能假设原来源永远可重取。首期接受单节点故障期间暂停并恢复；备份计划、预算和恢复目标须由部署验证，不承诺高可用或未经测量的 SLA。

`BLOCKED` 是不可消费诊断，不是已成功冻结的来源包。已冻结 Receipt 只描述签发时的决定；过期或存储损坏的包仍有历史身份，但当前禁止新准入。目录只证明本次完整枚举并验证的选定集合，不承诺操作系统点时原子快照；目录名、mtime 或未闭合扫描不能证明同源、未修改或删除。

## 被否决方案

### 实时本地目录或脏工作树来源

否决原因：其他 operator 无法重放其内容，本地编辑还可能在登记后静默改变分析证据。这并不否决用户选择的目录，只要它已被完整采集、验证并密封于 Traqen 受控存储。

### 自动组件覆盖，或将目录伪装为 Git 身份

否决原因：同名文件可能静默隐藏另一来源，且目录没有 Git commit graph。来源包必须保留每个组件的原生身份和带命名空间的定位符。

### 每个版本都全量上传或全量复制存储

否决原因：产品必须为变更分析保留完整、可比较的版本，却不能无谓重传未变化数据。已选目录仍须完整枚举以证明删除；仅未变化字节可复用，绝不凭空假定。

### 首期自动持续同步来源

否决原因：它会制造版本噪音、意外改变基线并带来不可控采集成本。用户显式创建新版本；webhook/watcher 策略未来可在独立治理合同下重新讨论。

### 任意范围规则或材料类型选择

否决原因：用户可在“扫描成功”的同时意外遗漏文档、配置、SQL 或测试。全 Git 仓库或一个声明根，加上一个完整选择的目录组件，是可理解的首期边界；规则语言不是。

### 所有 Gap 阻断，或每个 Gap 都可接受

否决原因：全阻断会使常见遗留仓库无法使用；完全可接受会让完整性和权限失败退化为点击警告。仅非阻断 Gap 可接受，才能同时保持流动与真实。

### 用扫描成功或零 Gap 作为发布条件

否决原因：作业完成不能说明输入完整性；零 Gap 会诱导掩盖已知限制。冻结 manifest、明确处置、对账和独立 Receipt 维度使限制可审计。

### 下游直接访问来源

否决原因：它绕过已密封来源，并允许后续能力从 Receipt 从未记账的材料中导出结果。F002 是唯一直接消费者；F003/F004 经由其输出继承 provenance。

### 将保存、保留与恢复全部留作实现细节

否决原因：用户能否在重启、关页、来源离线或磁盘满后保有同一证据，是 F001 的产品合同而不是存储接口的内部选择。必须在设计中明确落点、恢复语义与验收；原 `SnapshotStore` 抽象不能代替这些决定。

### 先密封整包再接受 Gap，或在冻结时延长接受期限

否决原因：前者与第 7/8 站的用户旅程矛盾，后者改变用户授权期限。采用先有效接受后原子发布、签发与消费重验绝对时间；内容不变的续签新建 Receipt，不重采材料。

### 默认清理草稿、只备份数据库或依赖原来源重抓

否决原因：会丢失用户期待可恢复的任务或目录唯一副本，并使旧 Receipt 指向不可恢复字节。保留默认持久化，回收显式授权，数据库与引用内容配套备份；损坏必须阻断，不能呈现 false green。

### 首期同时引入多后端和多节点高可用

否决原因：当前已接受单节点故障停机恢复的价值取舍。先把一条持久化/备份/恢复链验收完整；未来若要求故障中持续服务，应重新设计部署与存储合同，而非暗中承诺单节点具备高可用。

## 影响

- 产品用户选择一种来源类型或两来源组合、Git 授权/版本/目录根，以及要上传的目录。平台策略拥有安全、完整性和 Gap 严重度控制。
- 目录上传会得到清晰的已验证文件数。它只承诺所选目录的 Receipt 完整性，不声称所选文件夹外的材料存在或不存在。
- 根范围 Git 组件绝不能声称全仓库覆盖，组合来源包也绝不能暗示已自动调和冲突路径。
- 每个新版本拥有完整逻辑历史，而存储可安全复用已验证数据。即使无须全量上传字节，发现目录删除仍需完整重新枚举。
- 从来源包经由 F002 导出的每条下游事实、候选、主张、执行结果或影响建议都保留非阻断 Gap。
- 将来支持同类多组件、归档、自动同步、本地伴随扫描或跨租户内容复用时，必须新建来源身份与安全合同，不能作为未标记选项加入。
- 原型八站仍在同一来源快照工作台，容量、恢复和备份属于其生命周期；不新增 F005 全局导航模块。本次仅中文文档更新，不宣称 HTML/PNG 或产品代码已实现新增合同。

## 验证

- 对相同 Git commit 和/或已验证目录 manifest 在相同策略下重放，验证相同组件/来源包身份和 inventory 完整性结果；
- 验证目录 Receipt 在所有已选文件均验证前不会签发，且其身份不就选定目录外的材料作任何声称；
- 验证 Git A→B 和目录 D1→D2 产生完整新版本、只传输变化字节，且每个新增/修改/删除均由两份 manifest 推导；
- 验证组合来源包中 Git/目录同名路径可被分别查询；
- 验证 branch 移动或本地目录变化不改变已密封版本；
- 验证范围内每项恰有一个处置，且不输出敏感原文；
- 验证已接受非阻断 Gap 对 F002 消费者仍可见；
- 验证路径逃逸、初始目录完整性失败、完整性失败或不可信来源身份持续为 `BLOCKED`，且不能变为可消费；以及
- 验证有界流式/恢复永不暴露 Draft snapshot，且 F002 拒绝合格 Receipt 之外的输入。
- 验证断开原来源与服务重启后仍能核验冻结包，关页不丢任务，目录重选须核对，容量不足不删历史；
- 验证接受在发布前有效、绝对期限不平移、续签只新增 Receipt，旧事实 provenance 不变；
- 验证文件写入后事务失败、事务成功后丢响应、重复 seal 和执行持有者切换不产生半包或重复版本；
- 验证数据库与所有引用字节的配套备份能在隔离环境恢复；少一项即禁止准入，备份成功与冻结成功分别展示。
