# TestSpec 生成和批准验证 — 2026-07-14

## 结果

此切片在协议、应用程序、HTTP 和持久性边界处关闭了 MVP 接受项 7：当前授权的端点规则可以确定性地转换为可审查的 TestSpec 草案。转换不会创造新的业务真相，也不会授予自己的执行批准。

生成的记录保留准确的 Claim 版本、Decision、实现映射、Snapshot 清单、端点 Fact、转换器 identity/version 和规范的生成请求指纹。这使得规则到测试的链接变得可解释，并防止重试或稍后的批准掩盖原始草案。

## 安全和权限边界

- 仅支持标准 `endpointExposed EQUALS true` Claim 和当前 `CONFIRMED` 或 `EXCEPTION_RECORDED` Decision。
- 端点 Fact 必须属于所请求的 Snapshot 清单的活动实现映射。
- 生成的 TestSpecs 始终是版本 1、未经批准的草稿。转换器无法单独提供审批者或使草案可执行。
- 公共手册创建还仅接受未经批准的草稿，并拒绝客户提供的 `approval`、`origin` 或 `createdAt` 字段。
- 批准是一个新的不可变版本。审核者身份和角色来自受信任的解析者；允许的角色来自项目策略；时间和请求指纹是服务器生成的。
- 当任何确定性阻碍因素仍然存在时，批准就会失败。因此，受控写入需要显式的服务器识别的种子前提条件、清理策略、断言和批准。
- 字面上的秘密仍然被拒绝。生成的标头和正文只能引用本地解析的变量或 `secretRef` 值。
- 破坏性和外部副作用的操作级别仍然被阻止。

## 幂等性和历史

即使存在已批准的版本，使用相同的不可变请求指纹进行生成重试也会返回原始未经批准的草稿。重复使用的 TestSpec ID 与不同来源发生冲突。由相同的参与者、角色、预期版本和理由重试批准会返回现有批准的版本；不同的批准决定发生冲突。

PostgreSQL 验证执行公共草案和审批工作流程、租户绑定审批者强制执行、仅附加版本、每个 TestSpec 版本的精确 Claim 链接以及最新版本 Feature 基线选择。不需要架构迁移，因为出处和批准详细信息存储在现有的不可变 TestSpec 规范文档中。

## 验证

- `npm test`：通过了 109 项测试。
- 合约 JSON 解析：成功解析 OpenAPI、TestSpec 和 TestSpec 生成模式。
- 覆盖范围包括转换器资格、安全读取和受控写入分类、Seed/cleanup 间隙、不受支持和未经确认的 Claim 拒绝、客户端批准欺骗、身份验证、项目角色策略、批准幂等性、批准前后的生成幂等性、不可变 PostgreSQL 版本、租户隔离和现有 Feature 可追溯行为。

## 垂直闭合延续

随后的受控写入 Runner 切片关闭了此处描述的执行边界：生成可以显式绑定端点路径参数并通过查询目录引用添加审阅者提供的数据库期望； Runner 然后执行种子、列入许可名单的 API 写入、只读数据库验证、保证清理，并为相同的 TestSpec、Snapshot 清单和部署签名 Evidence。转换器仍然无法推断数据库业务期望 - 提供的草案仍然需要经过独立的人工批准。
