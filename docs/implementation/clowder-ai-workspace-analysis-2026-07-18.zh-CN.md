# Clowder AI Workspace 扫描验证 — 2026-07-18

## 目标与来源

本次验证使用真实公开仓库 [`zts212653/clowder-ai`](https://github.com/zts212653/clowder-ai)。其 README 将项目描述为一个基于 TypeScript/pnpm 的多 Agent 编排平台，包含 API、Web、MCP、共享记忆、身份、协作与集成能力。

- 默认分支：`main`
- 固定源码提交：`d606aab859883422b04d996cf223560fc20ae232`
- Git 报告的仓库文件数：5,357
- Traqen 实际分析的源码聚焦 checkout 记录：4,802
- 受支持记录：4,621
- 跳过记录：181

checkout 有意只物化静态 Feature 发现需要的产品源码、desktop、scripts、skills、feature-specification 和 SOP 范围，没有下载大型二进制资产与无关的非源码内容。Traqen 没有执行任何 Clowder AI 代码、没有安装其依赖，也没有把仓库文档视为已批准的业务权威。

## 第一轮真实扫描暴露的问题

扫描器版本 3 能处理该仓库，但输出还不能形成可读的功能树：

- 匿名路由回调被展示为 `Async`，因为路由提取器把 JavaScript 关键字误当成处理器名称；
- 每个导出常量、Schema、测试辅助函数、Mock 和 fixture 都可能被晋升为 Feature 候选；
- 通用词重合使几乎每个候选都被关联到测试；
- 项目全局 package/configuration 文件使每个候选看起来都有配置；
- 功能树只分出八个宽泛模块，数千个叶子直接堆在发现类型下。

这些属于扫描器质量问题，不是被分析仓库的缺陷。

较大的发现区域包括 API 的 `Cats`（653 个候选）、`Config`（200）、`Harness Eval`（176）、`Memory`（147）和 `Connectors`（97），以及 Web 的 `Shared UI`（323）、`Hooks`（123）、`Settings`（105）和 `Memory`（49）。这些名称与边界来自源码路径和路由结构，是导航假设，不是已经批准的产品分类体系。

## 追溯含义

- 4,324 个候选的业务权威全部保持 `PENDING`，实现符合性全部保持 `PARTIAL`。
- 4,324 条证据链全部不完整，因为尚无授权人员确认业务说明，也没有可信 Runner 回传与部署绑定的执行 Evidence。
- 扫描共记录 14,639 个阻断级 TraceGap，覆盖缺少业务权威、实现审核、已批准 TestSpec 和当前执行结果等问题。
- 明确不符合仍为 0。未知或未审核状态不会被静默改写成失败。
- 1,941 个关联测试文件只是代码级线索，不是已批准 TestSpec，也不是执行结果。

这正是 Traqen 实现愿景要求的行为：大型仓库可以发现大量实现候选，但平台不能假装静态扫描已经重建业务真相或证明了生产行为。

## 验证与剩余边界

Workspace 扫描器与构建回归测试已经通过，其中包含一个 Clowder 形态的测试工程，覆盖匿名 async 路由、可调用导出、常量/Schema 排除、辅助资产排除、保守测试关联和新增领域层级。

当前最终用户流程仍然是在浏览器中选择本地 checkout 进行扫描；本次验证没有实现 GitHub URL 直接导入。本轮由受控流程从 GitHub 获取 checkout，再交给同一个本地扫描器处理。未来的 GitHub 导入器必须保留相同的源码大小限制、秘密排除、增量 Snapshot 身份和“不得静默晋升业务权威”规则。
