# F001 — 工作空间与源码真相

**状态：** Spec — 方案已获 co-creator 确认；实现仍未获授权
**负责人：** CodeX
**关联：** F006 工作空间能力配置

## 为什么

Traqen 在解释存量系统或评估一次变更之前，必须证明它究竟检查了哪些材料，以及哪些材料没有取得。分支名、实时 checkout、目录名或“扫描成功”都不是证据。F001 将输入边界做成可重放、可见的事实，使 F002–F004 不能在输入不完整或后来已变化时把结论呈现为完整事实。

## 当前状态

此前 F001 收敛已确定不可变快照、明确处置、Gap 权限、Receipt 状态和 F002 准入。co-creator 现已确认完整来源模型：固定 Git 版本、上传目录或二者可以构成一个来源包；后续更新创建不可变增量版本，而不是重复上传未变化的字节。详细设计是当前产品设计真相源；更早的收敛记录保留为历史背景。

## 目标结果

F001 由至少一个来源组件建立一个 Workspace 范围内的 `SourceBundleSnapshot`：

- 一个已获只读授权的 Git 仓库：用户选择 branch、tag 或 ref 后，系统将其解析为精确的已提交版本；它也可以被限制在一个声明的仓库目录根内；
- 一个由用户选择并上传到 Traqen 受控存储的目录；或
- 两个组件同时存在。

首期的一个来源包至多包含一个 Git 组件和一个上传目录组件。组合包是**带命名空间的并集**，不是覆盖或自动合并：Git 与目录中同名的路径仍是两份不同产物，其身份是 `(componentSnapshotId, relativePath)`。

每个组件密封后不可变。来源包包含组件身份、`ArtifactInventory`、明确的 `CoverageGap` 和 `SourceTruthReceipt`。Receipt 状态为 `READY`、`READY_WITH_ACCEPTED_GAPS` 或 `BLOCKED`。F002 只获得合格来源包及继承 Gap，绝不获得可变路径、branch 名、实时工作树或上传会话。

当来源稍后发生变化，F001 创建逻辑上完整的新组件和新来源包版本，同时复用已验证、未变化的数据。Git 对比已提交 tree，只取得新增或修改的 blob。目录则由用户再次选择；客户端完整枚举并计算文件哈希，从而能知道新增、修改和删除，再只上传服务端尚未保存的字节；服务端会再次验证传入字节。结果是新的已密封来源真相，绝不编辑旧版本。

F001 不推断业务含义、不解析 API、不运行测试，也不宣称变更影响。它提供可信版本和文件级变更证据，由 F002、F003、F004 在各自责任范围内使用。

## 用户旅程

1. 架构师创建或打开一个 Workspace，分别添加**Git 来源**和/或**目录资料**。至少要有一个；两个都添加时，它们共同定义本次分析范围。这是两个可选输入，不是三选一。
2. 对 Git，架构师选择 branch、tag 或 commit；Traqen 在采集前解析并展示精确 commit。对目录，架构师选择一个文件夹；Traqen 展示已选文件总数，只有每个已选文件都接收并验证后才称上传成功。
3. Traqen 自动预检授权、来源身份、版本/目录根、上传/会话边界、路径、策略限制和采集安全，给出**可开始**、**可带预期 Gap 开始**或**已阻断**，并说明可执行的原因。
4. 系统冻结 manifest，安全采集材料，并为每个已发现条目记录一种处置。组合输入还会记录每一条目的组件身份。
5. 架构师审阅 Source Coverage、来源包 Receipt、组件、Artifact Inventory 和 Gap。只有非阻断 Gap 可携带负责人、理由和有效期被接受。
6. 来源材料变化时，架构师显式选择**创建新版本**。F001 按需要新建 Git 和/或目录组件，组装新来源包，并从选择的基线记录文件级新增/修改/删除 Delta；它不会静默跟随移动 branch 或本地目录。
7. F002 获得合格的 F001 来源包及继承 Gap。F004 稍后通过 F002 的结构化证据比较两个版本；F001 本身不下影响结论。

## 范围

### In scope

- 一个 Workspace，以及包含一个 Git 组件、一个目录上传组件或两者的来源包。
- 一个中文优先的 Source Truth 页面，提供两个彼此独立的来源卡：**添加 Git 来源**和**选择目录**。至少存在一个组件后才可运行预检；两个都添加不会生成第三种来源类型。
- 只读授权的 Git 登记；在采集前将选定 ref 解析为精确 commit；全仓范围或一个可选的仓库目录根。
- 将用户选择的一个完整目录上传到 Traqen 受控存储，并给出明确的成功文件数（例如 `20 / 20 verified`）；只要已选文件仍未验证，就不产生成功 Receipt。
- 自动预检身份、权限、版本、声明边界、路径安全、策略限制、外部内容边界和采集安全。
- 不可变的组件和来源包身份：来源坐标、声明范围、manifest/完整性摘要、采集时间和采集策略版本。
- Artifact Inventory：带组件限定的产物定位符、类型、大小、已采集时的安全内容摘要、一种处置及其原因。
- 已采集、仅展示脱敏、策略隔离、不可得、不可读、失败与范围外的明确覆盖状态。
- 非阻断 Gap 的接受：责任、理由、有效期和下游继承。
- 手动创建增量版本与历史：Git tree 对比、目录重新枚举和哈希对比、文件级 `add`、`modify`、`delete` Delta。
- 有界、流式的采集管线：在不把来源树或完整文件都装入内存的前提下，为 100,000 个文件建立可信来源包。

### Out of scope

- 首期一个来源包中多于一个 Git 组件或多于一个目录上传组件；组件的自动覆盖/合并；同路径的歧义消解。
- 未提交或脏工作树；归档解压；Git hook、filter、构建、依赖安装、仓库执行或来源修改。
- 持续 branch 监听、webhook、本地目录 watcher、自动建新版本、重命名/移动相似度识别，以及免除目录重新枚举的上传 Delta 协议。
- 用户自定义 glob/regex 规则、“仅代码”等材料类别开关，或用户控制安全、完整性和 Gap 严重度规则。
- 提取事实或构造 API 树（F002）；LLM 语义解释、人工审阅或业务功能树（F003）；测试执行证据、影响分析和复验建议（F004）。

## 必需记录

| 记录 | 最小字段和不变量 |
| --- | --- |
| `Workspace` | Workspace ID、成员、来源登记，以及版本、覆盖、历史和权限的隔离。 |
| `GitSourceRegistration` | 仓库身份、凭据引用、请求 ref、解析 commit 和可选仓库根。绝不保存裸凭据；ref 绝不是 snapshot 身份。 |
| `DirectoryUploadSession` | Workspace、上传者、所选目录标签、上传会话、冻结候选 manifest 和审计元数据。它至少含一个已选文件；所有已选文件验证前不是成功来源。 |
| `SourceCaptureRun` | 一次可审计的预检/采集/seal 尝试、进度 checkpoint、取消与重试关系。重试是新 run。 |
| `SourceManifest` | 一个组件按序、内容寻址的文件条目与分片摘要。它是覆盖和新增/修改/删除比较的权威。 |
| `GitSourceSnapshot` / `DirectoryUploadSnapshot` | 一个组件的完整已密封状态，保留原生身份：Git 是 commit/tree，目录是 upload/manifest 摘要。两种类型不能相互伪装。 |
| `SourceBundleSnapshot` | 不可变的有序组件引用、包级 inventory/Gap 与包摘要。至少有一个组件；不同组件同路径绝不相互覆盖。 |
| `ArtifactInventoryItem` | 来源包和组件 ID、相对路径、类型、大小、已采集时的安全内容摘要、处置和原因。每个已发现条目恰有一种终态处置。 |
| `CoverageGap` / `GapAcceptance` | 受影响组件/范围、严重度、原因、下游影响和跟进；接受记录追加写入，且只适用于有负责人、理由、有效期的非阻断 Gap。 |
| `SnapshotDelta` | 两份已密封 manifest/来源包的派生比较，操作为 `add`、`modify` 或 `delete`。可以缓存，但总能从 manifest 重新生成。 |
| `SourceTruthReceipt` | 分离的组件身份、范围、完整性、覆盖、Gap、接受、版本谱系，以及 `READY` / `READY_WITH_ACCEPTED_GAPS` / `BLOCKED` 可消费状态。 |

不可读、跳过、策略隔离、不可得或失败的条目绝不静默消失：它会出现在 inventory 中，并在限制后续分析时生成 `CoverageGap`。敏感原文绝不经由 Receipt、Inventory、UI 或诊断输出。仅展示脱敏的条目仍可为获授权下游分析所用；若脱敏令分析无法取得材料，则必须生成 Gap。

## 增量版本合同

每个版本在逻辑上始终完整且不可变，即使其物理字节被复用。完整的已密封 manifest 而非 Delta 才是来源真相；`SnapshotDelta` 是可重放的派生视图。

| 来源更新 | 发现变化 | 传输/存储行为 | 版本结果 |
| --- | --- | --- | --- |
| Git 从 commit A 变为 B | 按路径与 blob identity 比较两份已提交 tree。 | 只取得租户范围内已验证存储尚无的新增/修改 blob；删除只记录而不取得内容。 | 新 `GitSourceSnapshot`、新来源包和文件 Delta。 |
| 再次选择目录 | 客户端完整枚举并哈希所选目录；这是证明删除所必需的成本。 | 服务端比较 manifest；客户端只传新增/修改的缺失字节，服务端在 seal 前重新哈希。 | 新 `DirectoryUploadSnapshot`、新来源包和文件 Delta。 |
| 组合输入仅一个组件变化 | 复用未变化的已密封组件。 | 不复制或重传未变化且已验证的数据。 | 新来源包引用新组件与原有未变化组件。 |

首期将重命名或移动视为一次删除加一次新增。新版本由用户手动启动；branch 的移动既不能改变已密封版本，也不能静默成为新基线。

## 采集安全、规模与真实性

采集管线有界且流式：解析来源或创建上传会话 → 预检 → 枚举 → 冻结 manifest → 规划去重 → 经有界队列读取/哈希/存储 → 对账 inventory 和 Gap → 准备 seal → 原子发布已密封组件、来源包和 Receipt。Git 直接读取已提交 tree/blob，绝不读取可变 checkout。目录上传直接流向受控存储，不要求所有字节先代理通过应用后端。

- 不会仅因来源树或文件很大就把它们整体加载进内存；worker、队列、在途字节、文件描述符和元数据写入均有上限。Manifest 与 Inventory 分片、可搜索、可筛选、可分页，不渲染十万行页面。
- 物理内容复用限制在租户/Workspace 策略边界内；系统不通过去重行为泄漏跨租户内容是否存在。
- Capture run 会 checkpoint 安全的暂存工作。瞬态失败可借助已验证暂存 blob 恢复或重试，但 `DRAFT` 数据对 F002 不可见；只有原子 seal 才令组件/来源包可消费。
- Seal 会核验 manifest 分片、inventory 总数、字节总数、终态处置、已存 blob 和实质 Gap。worker 队列为空不等于成功。
- 来源身份失败、路径逃逸、篡改或策略冲突等安全/完整性失败均为阻断，不能被接受。对上传目录，已选文件必须被完整接收和验证才计入已选文件成功数；策略拒绝会阻断结果，而不是变成部分成功。已经验证但因大小、二进制/外部处理或获准脱敏而限制分析的条目，仅在策略将其分类为非阻断时才能成为可见 Gap。

在 100,000 个文件规模，成功意味着：固定的 Git+目录 fixture 可被采集和重放为同一身份；内存/队列/文件描述符上界受控；中断的 run 恢复后没有缺失或重复 inventory；没有部分 snapshot 到达 F002；租户隔离完整。实际吞吐应针对部署的存储、网络和资源预算测量，不承诺虚构的通用 SLA。

## 验收标准

- [ ] **AC-A1：** 架构师可登记只读授权的 Git 来源、选择 ref，并在采集前看到它被解析为精确 commit。
- [ ] **AC-A2：** 架构师可选择一个目录；成功结果证明每个已选文件均被接收且验证，部分目录没有合格 Receipt。
- [ ] **AC-A3：** UI 分别允许只有 Git、只有目录或各一个，并要求至少一个。组件身份始终可见，同名路径保持独立且不互相覆盖。
- [ ] **AC-A4：** 对相同组件输入、范围和采集策略的两次采集得到相同的组件/来源包身份和 inventory 完整性结果；之后的 branch 移动或目录重选不改变旧版本。
- [ ] **AC-A5：** 每个已发现条目恰有一种处置和原因；不可读、脱敏、排除、不可得、失败或范围外材料不被静默遗漏。
- [ ] **AC-A6：** Git commit 更新和目录重新选择都创建一份新的完整已密封版本，但只传输变化字节；由 manifest 派生的 Delta 记录所有新增、修改和删除。
- [ ] **AC-A7：** 采集不执行用户提供代码，也不经由 Receipt、Inventory、UI 或诊断暴露敏感原文；阻断条件不能因接受而变为可消费。
- [ ] **AC-A8：** 非阻断 Gap 被记录接受后仍可见且被 F002 继承；F002 拒绝直接来源定位符、不完整数据、过期接受和 `BLOCKED` Receipt。
- [ ] **AC-A9：** 100,000 文件的组合采集是流式、可重启、原子 seal、已对账且不能产生 false-green Receipt。

## 参考试点

试点使用带 commit A/B 的受控 Git fixture，以及带版本 D1/D2 的配套目录。组合包 A+D1 包含代码、文档、配置、SQL、测试、已安全处理的敏感 fixture、重复内容、零字节文件、深层路径以及一个刻意设置的非阻断限制。它必须证明：

1. 只有 Git、只有目录及组合来源包都显式呈现原生组件身份，且没有路径覆盖。
2. 目录成功 Receipt 只在其已选文件总数全部验证后签发。
3. A→B 只取得变化的 Git blob；D2 的选择完整发现新增/修改/删除，却只传输变化的目录字节。
4. 只有 Git 改变时复用未变的 D1 组件；旧 A+D1 与新 B+D1 包可独立查询。
5. 策略/阻断 fixture（如路径逃逸或完整性不匹配）为 `BLOCKED`，没有接受入口，也不能进入 F002。
6. 100,000 文件的组合 fixture 可重启、对账完整、资源有界，且绝不向 F002 暴露 `DRAFT` 数据。

## 开放问题

已确认的产品边界没有开放问题。连接器、存储引擎、队列大小和部署资源预算属于实现规划，且不得削弱本合同。

## 依赖与交接

F001 是 F002–F004 的来源证据边界。F006 提供相关 Workspace 能力配置；F001 的来源采集不运行 Agent。只有 F002 可将合格来源包、inventory、继承 Gap 和可选的 F001 Delta 转换为确定性事实及 API 结构投影。F003 用 F002 事实建立经审阅的业务含义。F004 仅从这些下游结构/语义结果和选定版本 provenance 进行影响分析。
