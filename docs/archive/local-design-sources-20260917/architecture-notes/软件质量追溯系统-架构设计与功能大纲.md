# 软件研发质量追溯系统 —— 架构设计与功能大纲

> 定位：不做SBOM（已成熟，直接集成现成工具），聚焦"结构依赖图"（确定性）+"语义追溯图"（概率性）两层，外加贯穿全程的"往前捕获"主线。

---

## 一、设计原则（贯穿全文，决定所有技术选型的取舍）

1. **结构层用确定性算法，语义层用概率性方法+人工兜底** —— 两层的信任等级不同，不能用同一套标准要求。
2. **往前捕获 > 历史回填** —— 新增内容的结构化捕获成本低、无信息损耗；历史回填受信息论限制，是"尽力而为"的背景任务，没有"完成"的终点。
3. **不做大而全，先在一个真实场景里验证核心假设** —— 单个活跃团队/模块试点，跑通再推广。
4. **能买的不造** —— SBOM、代码依赖解析（Tree-sitter/LSP）、图数据库这些已经是成熟基础设施，精力应该花在语义层和往前捕获流程的产品化上。
5. **诚实分层承诺** —— 结构层可以给强承诺（"输入代码，输出可靠的影响分析"），语义层只能给"自适应辅助"的承诺，避免制造虚假确定感。

---

## 二、总体架构

```
┌─────────────────────────────────────────────────────────┐
│  Layer 4  应用/门禁层                                      │
│  PR集成 · CI门禁 · MCP接口(AI Agent用) · 仪表盘 · 审计报表    │
├─────────────────────────────────────────────────────────┤
│  Layer 3  图存储与查询层                                    │
│  统一图数据模型 · 版本/基线管理 · 查询API(正向/反向/路径)      │
├───────────────────────┬─────────────────────────────────┤
│  Layer 2 语义图谱引擎    │  Layer 1 结构图谱引擎              │
│  (概率性 + HITL兜底)     │  (确定性算法)                     │
│  三元组抽取·语义召回      │  AST解析·调用图·依赖图·增量更新      │
│  置信度校准·实体消歧      │  Blast Radius计算·风险打分          │
├─────────────────────────────────────────────────────────┤
│  Layer 0  数据接入层                                        │
│  Git连接器 · 文档连接器(可插拔) · Tree-sitter/LSP · CI Webhook│
└─────────────────────────────────────────────────────────┘
        ↕ 横向贯穿：治理与反馈层
   权限管理 · 审计日志 · ID规范/往前捕获流程 · 人工反馈闭环
```

## 三、分层详细设计

### Layer 0　数据接入层
- **Git连接器**：commit历史、diff、blame、PR/MR描述
- **文档连接器**：适配器模式，插件化对接Confluence/Wiki/飞书文档/Word等，不同组织文档系统差异大，必须做成可扩展接口而非硬编码
- **代码解析**：Tree-sitter（多语言AST，支持增量解析）+ LSP（符号解析、跨文件引用）
- **CI/CD Webhook**：commit/PR事件触发增量分析，而非定时全量扫描

### Layer 1　结构图谱引擎（确定性，优先建，建议buy为主）
| 功能 | 说明 |
|---|---|
| 多语言AST解析 | 基于Tree-sitter，覆盖团队实际使用的语言栈 |
| 调用图/依赖图/导入图构建 | 编译器技术范畴，算法确定，无AI不确定性 |
| 增量更新引擎 | 内容寻址哈希+文件状态缓存，只重新分析变更文件 |
| 跨仓库依赖发现 | 针对共享库/Terraform/Docker基础镜像等跨仓库场景 |
| Blast Radius计算 | 从改动点出发做图遍历(BFS/DFS)，输出受影响节点集合 |
| 风险打分 | 测试覆盖率 + 下游消费方数量 + 历史变更频率加权 |
| 门禁判定 | 输出PASS/WARN/BLOCK，接入CI |

### Layer 2　语义图谱引擎（概率性，需HITL兜底，重点自研）
| 功能 | 说明 |
|---|---|
| 文档分块 | 重叠切片，避免跨片段实体/关系被切断 |
| 实体类型标注抽取 | LLM三元组抽取，提示词明确实体类型(需求/设计/测试) |
| Embedding语义召回 | 解决"同一事物不同叫法"的候选匹配问题 |
| LLM关系判定 | 二次判断关系类型+置信度打分，提示词工程是效果关键变量 |
| 置信度校准 | 确保"90%置信度"真的对应约90%正确率，而非虚高分数 |
| 分层路由 | 高置信度自动采信 / 低置信度自动丢弃 / 中间地带进人工队列 |
| 实体消歧/聚类 | 缓解图谱碎片化，目前业内公认的薄弱环节 |
| 主动学习反馈闭环 | 优先把"审核后最能提升整体准确率"的样本给人看 |
| 抽样复核 | 对已自动通过结果做随机抽样监控漂移 |

### Layer 3　图存储与查询层
- **统一图数据模型**：节点类型(需求/设计/代码/测试/组件)，边类型(实现/验证/依赖/调用)
- **存储选型**：小规模SQLite邻接表即可，规模上升后迁移Neo4j/Memgraph
- **查询API**：正向追溯(需求→代码)、反向追溯(代码→需求)、路径查询、影响分析
- **版本/基线管理**：类比PDM的"工程变更单"概念，追溯关系本身也要有版本历史

### Layer 4　应用/门禁层
- **PR/CI集成**：影响分析结果展示在PR页面，高风险改动强制门禁
- **MCP接口**：暴露给AI编码Agent，改代码前主动查询依赖图和追溯关系
- **仪表盘**：孤儿需求(无代码实现)、未测试代码、追溯覆盖率趋势
- **审计报表**：面向合规场景(车规/医疗)导出"需求→设计→代码→测试"证据链

### 横向　治理与反馈层
- **权限管理**：不同角色对图谱数据的访问/编辑权限
- **审计日志**：谁在什么时候确认/修改了哪条追溯链接
- **ID规范工具**：统一需求/变更命名规范(如REQ-*)，配套commit/PR强制关联的轻量插件
- **反馈闭环**：人工修正记录 → 用于置信度重新校准和提示词迭代

## 四、功能大纲（按实施阶段分P0/P1/P2）

### P0 —— 阶段0-1：试点验证（结构层+往前捕获）
- [ ] 选定试点团队/模块，确认基本PR review和测试覆盖习惯已具备
- [ ] Git连接器 + Tree-sitter/LSP解析接入
- [ ] 调用图/依赖图构建 + 增量更新引擎
- [ ] Blast Radius计算 + CI集成(先warn-only，观察误报率)
- [ ] 定义ID命名规范，commit/PR强制关联(轻量、AI辅助生成建议)
- [ ] 基础仪表盘：显示依赖图和影响分析结果

### P1 —— 阶段2-3：语义层接入(限定范围)
- [ ] 文档连接器(先接入试点团队实际在用的1-2个文档系统)
- [ ] 三元组抽取pipeline + Embedding语义召回
- [ ] 置信度打分 + 分层路由 + 人工审核队列UI
- [ ] 结构层门禁从warn-only切换为强制block(高风险改动)
- [ ] 语义层历史回填：仅覆盖当前正被触碰的模块(结合bug修复/功能开发顺手补)
- [ ] 置信度校准机制上线

### P2 —— 阶段4：规模化与闭环
- [ ] 主动学习引入，降低长期人工审核负担
- [ ] 实体消歧/聚类优化
- [ ] MCP接口开放给AI编码Agent
- [ ] 审计报表(面向合规场景)
- [ ] 跨仓库依赖发现(如需扩展到多仓库场景)
- [ ] 视试点效果决定是否扩大范围/推进跨语言泛化

## 五、Build vs Buy 建议

| 组件 | 建议 | 理由 |
|---|---|---|
| SBOM | Buy(Syft/Trivy/Dependency-Track) | 已标准化，自研无意义 |
| 代码解析(Tree-sitter/LSP) | Buy/复用开源 | 成熟基础设施 |
| 结构依赖图/Blast Radius | Buy为主，视场景定制 | 技术确定性高，已有开源和商业方案 |
| 语义抽取+追溯 | 自研为主 | 核心差异化价值所在，且需要贴合组织实际文档习惯 |
| 往前捕获流程工具 | 自研(轻量) | 流程约束类工具，需紧贴团队实际workflow定制 |
| 图存储 | Buy(Neo4j/Memgraph) | 不需要重新发明图数据库 |

---

## 六、给你的下一步建议

不要在P0还没跑顺之前设计P1/P2的通用抽象层——核心假设(人工审核能降到多低、团队是否配合往前捕获流程)需要真实数据验证，过早为泛化性投入架构，容易在假设证伪后推倒重来。
