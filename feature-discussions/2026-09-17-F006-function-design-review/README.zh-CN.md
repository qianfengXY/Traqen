# F006：Workspace 能力设置 — 功能设计审阅稿

> **后续发布：** [功能与 UX 设计 V1.0](../../docs/design/F006-workspace-capability-settings/README.md) 已成为当前阅读入口。本文件保留审阅时的原始内容；其移动端建议等不再作为新版桌面 UX 的验收要求。

> **用途：** 让 co-creator 先核对 F006 的产品边界是否正确。本文是审阅稿，不替换现有 F006 规范、ADR 或生命周期状态；没有实施授权，也不表示 F006 已完成。

## 1. 一句话目标

管理员先在全局维护可复用的账号、CLI 模型和能力资产，再为每个 Workspace 明确配置一个 Main Agent、一个或多个 Child Agent 及其可用能力；用户可以保存未完成草稿，只有主动应用后才产生供未来运行使用的不可变配置版本。

F006 管的是“谁能在下一次分析中使用什么”，不是自研 Agent Runtime，也不执行 OAuth 登录、直接 API 模型调用或任意本地命令。

## 2. 用户看到的整体流程

流程是：全局设置的账号、模型、Skill 与 MCP → Workspace 的能力可用性、Main/Child 显式授权 → 可恢复草稿 → 主动 Apply → 不可变 Active Revision → 后续真实分析运行固定该版本。

前两层是 F006 的设置职责。最后一步的“真实分析启动、首次或配置变更后的确认、材料预检与运行恢复”应由 F003 的“分析准备”宿主消费 F006 的 Active Revision；它不是 F001 旧来源采集入口的职责。

## 3. 设置中心

### 3.1 入口与范围

用户从顶层“设置”选择：

1. **全局设置**：管理可复用资产；
2. **Workspace 设置**：选择一个 Workspace 后管理该 Workspace 的团队与能力。

Workspace 内的设置入口直接进入当前 Workspace。页面标题、面包屑和文字始终标识范围；颜色不能是唯一提示。

### 3.2 全局设置的四类资产

| 页面 | 用户管理什么 | 不能做什么 |
|---|---|---|
| 账号 | API Key 的 Secret 引用，或已安装 CLI 的 OAuth 登录状态 | 看见、保存或发起 OAuth Token/登录 |
| 模型 | 已允许的 CLI 与账号绑定、模型选择、就绪性检查 | 配置任意命令、参数或全局默认模型 |
| Skill | 可复用的 Skill 身份、来源、校验与全局可用性 | 自动授予任意 Workspace 或 Agent |
| MCP | 可复用 MCP 资产记录、来源、校验和全局可用性 | 把“已保存”误称为已经真实可执行 |

API Key 只进入认可的 Secret Store，F006 的界面、日志、历史版本和运行快照只保留非敏感引用与状态。OAuth 始终属于 CLI；管理员在 CLI 自身登录后，F006 只提供“重新检查状态”。

## 4. Workspace 设置

### 4.1 Agent 团队

每个 Workspace 始终有一个不可删除的 Main Agent，且默认展示一个未配置完成的 Child 1。Child 1 是显式的必填占位，而不是可运行的默认 Agent；用户可继续添加 Child。

每个 Agent 都要明确选择：

- 一个已就绪的全局模型；
- 从该 Workspace 生效能力中选择的 Skill/MCP 授权。

创建 Child 不得静默复制能力授权。F006 的最小激活条件是一个完整 Main 加至少一个完整 Child；未来某个分析策略可以要求更多 Child，但不能反向改变已经应用的设置版本。

### 4.2 能力管理和授权分工

能力管理页只决定“这个 Workspace 能否使用某项能力”；Agent 设置页只决定“哪个 Agent 被授予它”。两者不能混为一个隐式开关。

Workspace 能力页分四组显示：

1. 可用的全局继承能力；
2. 被当前 Workspace 禁用的继承能力；
3. 当前 Workspace 独立新增的能力；
4. 全局不可用或需要处理的能力。

第四组不是“Workspace 主动禁用”。每一项都应标出来源、健康状态、生效状态及已获授权的 Agent，并给出修复或移除授权的入口。Workspace 可禁用继承项或创建独立本地项，但不能同身份覆盖、fork 或字段级修改全局 Manifest。

## 5. 草稿、应用和版本

编辑设置自动保存为可恢复 Draft，Draft 可以不完整。用户选择 Apply configuration 后，系统校验 Main、Child、模型和实际授权能力；成功才新增不可变 Active Revision。

草稿不完整不是错误数据：用户可以离开、刷新后恢复，并继续修复。Apply 才是设置权威切换点；失败时必须说明具体对象及下一步，而不是清空草稿或改写历史版本。

每个 Active Revision 固定 Main/Child 的模型、显式授权、能力来源和非敏感账号标识。全局资产后续新增、草稿编辑或其他 Workspace 的修改，都不能静默改变该版本。

## 6. 全局变更的影响

停用或删除全局 Skill/MCP 前，服务器先计算影响到的 Workspace、Agent、生效版本和未来运行；删除还必须输入能力名称确认。

受影响 Workspace 显示“需要处理”，可移除授权、改用其他可用能力或创建本地替代。现有运行继续使用自己的固定快照。仅当某个 Active Revision 实际授权了已不可用能力时，才阻断新的运行；目录中一个未授权的条目不能阻断运行。

## 7. 桌面与窄屏体验

Workspace 设置外壳持续展示 Ready、Incomplete 或 Needs attention，并给出具体修复入口。

- 桌面端：团队卡片或列表与持久的 Agent 详情检查器并列；
- 窄屏：详情检查器改为全屏抽屉，并能回到团队；
- 所有页面：覆盖 loading、empty、error、conflict 和 recovery；失败既在对象卡片显示，也在页面层汇总，且均给出下一动作。

## 8. 安全与不变量

| 编号 | 产品保证 |
|---|---|
| INV-01 | API Key 不越过 Secret 边界，OAuth Token 不进入 Traqen。 |
| INV-02 | CLI 调用固定、白名单化，不接受用户 Shell 命令或任意参数。 |
| INV-03 | 全局不可用能力不能被 Workspace 重新激活或授予。 |
| INV-04 | 每个 Agent 的授权必是 Workspace 生效能力的子集。 |
| INV-05 | Draft 可以不完整；Apply 需要完整 Main 与至少一个完整 Child。 |
| INV-06 | 运行只消费其创建时固定的 Active Revision，不热切换。 |
| INV-07 | 缺失资产只阻断实际授权它的 Active Revision。 |

## 9. 当前交付状态：已通过的设置旅程

下列设置层能力已在合入后的隔离验证中通过：

- 四个全局设置页面、Workspace 范围切换和桌面/375px Agent 详情；
- API Key 的 Secret 引用提示、CLI-owned OAuth 状态检查和模型就绪性错误可见；
- 全局或本地 Skill 的创建、选择、显式授权、Apply 和不可变版本保存；
- Draft 自动保存、刷新恢复、409 冲突后的“重试我的草稿”及“采用服务器草稿”恢复；
- 全局能力删除影响预览、不可用授权修复和后续 Apply；
- Active Revision 固定，不受后续草稿改动影响。

这些证据说明 F006 的设置中心、权限边界和配置版本机制已交付；它们不自动证明后续分析入口已经消费了配置。

## 10. 尚未完成、不能误写为完成的两项

### 10.1 真实分析启动确认

F006 的产品要求是：第一次使用某个 Active Revision 启动分析、或之后应用了新版本再启动时，用户要看到 Main/Child 模型、能力数量和账号状态摘要并明确确认；版本未改变的重复启动不应反复打扰。

当前 helper 和版本冲突保护存在，但真正消费 F006 配置的新分析入口尚未完成。正确宿主是 F003 的“分析准备”，它还需要与 F001 的获准材料、F002 受控材料/参考、F006 的精确 Active Revision 建立受控启动合同。不能通过恢复 F001 的旧原目录启动入口来补齐这条旅程。

### 10.2 MCP 的真实执行

当前 MCP 可作为设置资产被记录、展示和授权，但没有受支持的生产执行器，因此“保存或 Apply 成功”不能被解释为 Agent 已能调用 MCP。co-creator 已明确：**现阶段不做 MCP**。

这不是把 MCP 标成已完成或永久取消；它表示不连接服务、不读个人 CLI 配置/凭据、不实现通用执行器。未来若重新进入该范围，必须先确认首个真实业务用途、数据边界、部署隔离与 CLI OAuth 兼容性，再定义完整设计并另行获准实施。

## 11. 这版刻意不做什么

- Traqen 驱动 CLI OAuth 登录或保存 OAuth Token；
- 直接 API 模型执行、自研 Agent 或用户输入的 CLI Shell 命令；
- 通过字段 patch、隐式继承或自动复制扩大 Agent 权限；
- 运行中或恢复时热切换到新的设置版本；
- 让“设置记录存在”替代“能力真实可执行”的证据；
- 恢复旧 F001 来源采集入口来伪装完成 F003 的分析启动确认。

## 12. 请 co-creator 核对的产品判断

1. F006 是否应继续定位为“可恢复、可审计的配置中心”，而不承担 F003 的分析执行界面？
2. Main 加至少一个 Child 是否符合期望，还是某类分析必须由 F003 在启动策略中要求更多 Child？
3. 在 MCP 暂停期间，MCP 是否保留为不可执行的设置资产，还是应在本阶段从用户可见设置中隐藏？本文不替你做该取舍。
4. F003 的“分析准备”是否应成为唯一的新分析入口，并消费 F001/F002/F006 的固定输入？

## 13. 与现有真相源的关系

- 现有 F006 规范仍是设置合同；本文只把其用户功能与当前交付状态翻译为一份可审阅设计稿。
- 现有 F006 规范第 9 节仍写 F001 消费执行快照，但当前跨功能核验确认真实新分析宿主应为 F003；在 co-creator 确认跨功能启动合同前，本文不修改该规范。
- 本文不改变 F001、F002、F003 的设计、代码、契约或生命周期。

## 14. 审阅后的下一步

若产品边界正确，下一步应先由 co-creator 确认：

1. 是否将 F003 分析准备、F001/F002 受控材料交接、F006 版本确认作为一个明确的后续交付范围；
2. MCP 的暂停在 F006 的正式范围中是临时保留还是正式降级。

在这两个判断明确前，F006 不能以“设置页已通过”标记为完成。
